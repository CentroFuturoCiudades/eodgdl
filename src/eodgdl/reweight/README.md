# Reweighting inputs for TMG.SurveyReweight

The IMEPLAN Guadalajara EOD 2023 ships three nested expansion factors (dwelling, person,
trip). This set is what [TMG.SurveyReweight](https://github.com/TravelModellingGroup/TMG.SurveyReweight)
needs to compute **one weight per household** instead: integer-keyed record tables, a zone
system with its aggregation maps, and constraint targets from the 2020 census (as shipped
in IMEPLAN's AGEB table) and from the two external controls the survey itself used.

Every household starts at weight 1.0 inside the tool; the `ExpansionFactor` columns here
are the survey's own weights, kept for comparison, and the tool ignores them unless a
constraint names them.

Generated by `eodgdl reweight build`. Every definition below is in
`src/eodgdl/reweight/spec.yaml`, which is the thing to edit.

## Files

| file | rows | what |
|---|---|---|
| `ZoneSystem.csv` | 90 | `TAZ,Zone,Municipality,Region`, all integers. Column 0 is the TAZ list; columns 1–3 are the three aggregation maps. |
| `ZoneLabels.csv` | 90 | What each TAZ is: `centralidad`, `municipio`, `CVE_MUN`, sampled dwellings. Not read by the tool. |
| `HouseholdRecords.csv` | 17,901 | `HouseholdID,HouseholdTAZ` + attributes |
| `PersonRecords.csv` | 58,061 | `PersonID,HouseholdID` + attributes |
| `TripRecords.csv` | 154,133 | `HouseholdID,PersonID,TripID` + attributes (`TripID` is an attribute the tool ignores) |
| `Constraints/HouseholdConstraintsByZone_{2020,2023}.csv` | 64 | `Zone` + six household targets |
| `Constraints/PersonConstraintsByZone_{2020,2023}.csv` | 64 | `Zone` + 23 person targets |
| `Constraints/PersonConstraintsByMunicipality_{2020,2023}.csv` | 9 | `Municipality` + `Cyclist` |
| `Constraints/TripConstraintsByRegion.csv` | 1 | `Region` + `BusBoardings` (already a 2023 figure, so one file) |
| `Constraints/constraints.csv` | 61 | One row per constraint: file, target column, its 0-based column index, table, geography, map column, matching attributes. The XTMF2 configuration, as data. |
| `Constraints/diagnostic_{2020,2023}.csv` | | Every target next to what the survey gives at its own dwelling weight (`viv.ponderador`): how far the shipped weights sit from each target before the tool moves anything. |
| `Constraints/coverage.csv` | 9 | The survey universe as a share of each whole municipality (population, dwellings, employed). |

Use one constraint set (2020 or 2023) at a time. The records are the same for both.

### Ids and zones

- `HouseholdID` = `folio_vivienda`; `PersonID` = `folio_vivienda × 10 + folio_habitante`
  (`folio_habitante` ≤ 9); `TripID` = `folio_viaje`.
- The survey is stratified by *centralidad* (64 zones observed of 71), but 22 of those zones
  straddle two or three municipalities, so neither is an aggregate of the other. The TAZ is
  therefore the **zone × municipality cell**: `TAZ = zone_index × 1000 + CVE_MUN`, where
  `zone_index` is the 1-based position of the centralidad code in the survey's ordered list
  (zone `05` → 5, `Aeropuerto` → 71) and `CVE_MUN` the INEGI municipality key (Guadalajara
  39, Zapopan 120, Tlaquepaque 98, Tlajomulco 97, Tonalá 101, El Salto 70, Juanacatlán 51,
  Ixtlahuacán 44, Zapotlanejo 124). `Zone` and `Municipality` are those two numbers;
  `Region` is 1 everywhere.
- No constraint targets the TAZ itself: seven cells hold fewer than 30 sampled dwellings.
  Zone constraints see 155–417 dwellings and 468+ persons per zone.

## Configuring the XTMF2 model system

```text
SurveyReweight
|- ZoneSystem: LoadZoneSystem
|  |- TAZ            LoadCategoriesFromCSV            ZoneSystem.csv  (column 0)
|  `- SuperZones     LoadCategoryMapFromThirdNormalizedCSV, three of them, all on ZoneSystem.csv:
|                      zone:         Base Column 0, Destination Column 1
|                      municipality: Base Column 0, Destination Column 2
|                      region:       Base Column 0, Destination Column 3
|- SurveyRecords: LoadSurveyRecords   (the loader's default key columns fit these files)
|  |- HouseholdFile  HouseholdRecords.csv   HouseholdIDColumn 0, HouseholdTAZColumn 1
|  |- PersonFile     PersonRecords.csv      PersonIDColumn 0,   PersonHouseholdColumn 1
|  `- TripFile       TripRecords.csv        TripHouseholdColumn 0, TripPersonColumn 1
|- Constraints: LoadConstraints
|  |- HouseholdConstraints   one LoadConstraint per row of Constraints/constraints.csv with table = households
|  |- PersonConstraints      ... table = persons
|  `- TripConstraints        ... table = trips
|- MaximumIterations, Damping, MinimumExpansionFactor, MaximumExpansionFactor
|- UpdatedExpansionFactorsFile
`- ConstraintReportFile
```

For each `LoadConstraint`, read its row in `Constraints/constraints.csv`:

| parameter | value |
|---|---|
| `File` | `Constraints/<file>` |
| `GeographyColumn` | 0 (always the first column) |
| `TargetColumn` | `column_index` |
| `MatchingAttributes` | `matching_attributes`, split on `;` (e.g. `Male;Age18_24` is the two attributes `Male` and `Age18_24`, whose product the tool sums) |
| `CategoryMap` | the super-zone map named by `map_column` (`Zone`, `Municipality` or `Region`) |
| `Constraint Name` | `target_column` |

Parameters worth setting deliberately:

- **`MaximumExpansionFactor`**: the default 50 is far below this survey. The dwelling design
  weights run 2–267 (mean 82), so the tool cannot reach the targets unless the ceiling is
  raised (500 is a safe start; the constraint report will show if it binds).
- **`MinimumExpansionFactor`**: 1 is fine; a household never stands for less than itself.
- **`Damping`**: with 31 constraints per set, several on the same persons, a value below 1
  (0.5–0.8) usually converges more smoothly than 1.
- `Tolerance` per constraint: 0.01 is the tool's default; the region-level `BusBoardings`
  may deserve a looser one (see caveats).

## Attributes

Household (`viv`): `Dwellings` = 1 · `Occupants` = `personas_en_vivienda` (all ages, top-coded 10) ·
`HasCar`, `HasMoto`, `HasBike` = at least one of `n_autos_camionetas`, `n_motos`, `n_bicicletas` ·
`HasInternet` = `tiene_internet`.

Person (`hab`, ages 6+ only): `Persons` = 1 · `Male`/`Female` from `sexo_nacimiento` ·
`Age6_11 … Age60p` from `edad` at the census cut points (6–11, 12–14, 15–17, 18–24, 25–59,
60+) · `Employed`/`Unemployed`/`Inactive`/`NotEmployed` from `trabajo_semana_pasada`, ages
12+ only (`Employed` = Tiempo completo, Medio tiempo, Tenía trabajo pero no trabajó;
`Unemployed` = Busco trabajo; `Inactive` = the other five answers; `NotEmployed` = everyone
12+ who is not `Employed`, the 4,370 with no answer included) · `Cyclist` = at least one
bicycle leg (Bicicleta, Mi Bici) on a trip whose motive is Trabajar or Estudiar.

Trip (`trips` after `load_eod`'s cleaning, without the 491 rows it marks as non-trips):
`Trips` = 1 · boardings = the number of the trip's legs by `Bus` (CAMIÓN O AUTOBÚS), `Rail`
(TREN LIGERO), `BRT` (MI MACRO), `Sitren` (lines 1–3), `OtherTransit` (Servicio suburbano,
Taxi colectivo, Transporte informal), and their sum `TransitBoardings` · `BicycleTrip` = any
bicycle leg.

## Targets

Census values come from INEGI's Censo 2020 through `mxcensus` (`load_census(state=14)`,
the AGEB and rural-locality frames). IMEPLAN's AGEB table (`RELACION_AGEBS-ZONA_con_datos_censales`)
is used only as the crosswalk from those to the survey zones: the rows with a 2023 zone
(`EOD2023 != 'NA'`, 2,026 AGEBs and 138 localities in 64 zones; the fringe micro-zones
outside the 2023 coverage are excluded) are joined to the census on their INEGI key, and
the build refuses to run if a zone's census population differs from IMEPLAN's. Wherever
both hold a value they are identical; `mxcensus` keeps suppressed cells blank where
IMEPLAN wrote 0 and imputes the ones its parent totals determine. Columns are summed by
zone or municipality, then combined:

| target | census |
|---|---|
| `Dwellings` | `TVIVPARHAB` — private inhabited dwellings, 1,454,608 |
| `Occupants`, `HasCar`, `HasMoto`, `HasBike`, `HasInternet` | `OCUPVIVPAR`, `VPH_AUTOM`, `VPH_MOTO`, `VPH_BICI`, `VPH_INTER`, each × `TVIVPARHAB / VIVPAR_HAB` per zone — these counts refer to the dwellings with occupant information (`VIVPAR_HAB`, 7 % fewer), so they are rescaled to the full base |
| `Persons` | `P_6A11 + P_12A14 + P_15A17 + P_18YMAS` — ages 6+ with a stated age, 4,635,931, so the age bands partition it; `POBTOT − P_0A2 − P_3A5` would be 1 % more |
| `Male`, `Female` | the `_M` / `_F` versions of the same |
| `Age6_11 … Age60p` | `P_6A11`, `P_12A14`, `P_15A17`, `P_18A24`, `P_18YMAS − P_18A24 − P_60YMAS`, `P_60YMAS`, and their `_M` / `_F` versions for the 12 sex × age crosses |
| `Employed` (zone) | `POCUPADA` — the occupied population, 12+ |
| `NotEmployed` (zone) | `P_12A14 + P_15A17 + P_18YMAS − POCUPADA` — everyone else aged 12+: unemployed, inactive, activity not specified. `PE_INAC` is not a target on its own: the survey's non-respondents would be forced to match the census's 16,000 unknowns |
| `Cyclist` (municipality) | Census 2020 extended questionnaire (via `mxcensus`): persons whose mode to work or to school is a bicycle, weighted; **101,907** over the nine whole municipalities, the INEGI figure IMEPLAN calibrated its person weights to. The microdata has no AGEB, so each municipality's count is scaled by the universe's share of its population (`coverage.csv`), which gives **100,453** |
| `BusBoardings` (region) | **1,851,750**, SETRAN's 2023 daily bus boardings, the control of the survey's trip weight |

**The universe is not the nine whole municipalities.** Guadalajara, Tlaquepaque, El Salto
and Zapopan are inside it to 99 % or more, Tlajomulco 98 %, Tonalá 97 %, Ixtlahuacán 89 %,
Zapotlanejo 76 %, Juanacatlán 33 % (`coverage.csv`). Every target here is a sum over the
universe; a whole-municipality figure from any other source must be scaled the same way
before it becomes a target.

**2023 set.** Each AGEB's census values are multiplied by the CONAPO 2023/2020 population
ratio of its municipality, pooled over the 5-year bands the target spans and over the sex it
names (6–11 → 5–14; 12–14 → 10–14; 15–17 → 15–19; 18–24 → 15–24; 25–59, 60+ as they are;
person totals and cyclists → 5+; economic activity → 10+; dwellings → all ages), then summed.
It is a municipal growth factor, not a projection of each zone. Study-area totals go from
1,454,608 to 1,497,534 dwellings and 4,635,931 to 4,793,198 persons 6+.

## Caveats

- **Sparse cells.** The sex × age crosses have as few as 3 records in a zone
  (`Male_Age12_14`). Every target with a positive value has at least one matching record
  (checked by `eodgdl reweight check`), but those households will carry large corrections.
  Drop the crosses if the weight range or the constraint report says so.
- **No unemployment control.** INEGI's unemployed (`PDESOCUP`, 40,391 in the universe)
  are the people aged 12+ without a job who looked for one in the reference week; anyone
  without work who did not look is inactive. The survey never asks about job search. Its
  `Busco trabajo` answer (122 persons, 13,704 at the design weight) is the closest match and
  gives a third of the census; its `ocupacion == Desempleado` answer (790 persons, 80,335)
  gives double, and only 102 people gave both. With the two proxies bracketing the target
  by a factor of three either way, no reliable target exists, so it was left out.
  `Unemployed` (the `Busco trabajo` reading) stays in the person records.
- **Bus boardings.** One household weight cannot scale a household's bus legs without
  scaling its car trips, and bus riders skew low-income, so matching SETRAN through the
  weight distorts the other margins (`reports/expansion_factors.qmd`, §6). It is here
  because it was asked for; treat it as optional and watch what it does to `HasCar`.
- **No income control.** The census has no income variable and 58 % of households did
  not report theirs; income is neither an attribute nor a target.
- **4,370 persons** gave no activity answer. They are 0 in `Employed`, `Unemployed` and
  `Inactive` and 1 in `NotEmployed`, so the two targets in use partition the 12+ population
  and nobody is left in a residual the census does not have.
- **Under-6s** are absent from the person records (the survey interviews 6+); `Occupants`
  counts them on the household side.
- **Cyclist** uses the census commute definition; IMEPLAN's own reweighted set was narrower
  and cannot be reproduced from the shipped columns.
- **Suppression.** INEGI blanks cells of one or two units. Sums skip them, so the sexed
  targets fall short of the unsexed ones by up to 39 persons in a few zones (427 in all).

## Regenerating

Needs the `reweight` extra (`uv sync --extra reweight`), which brings `mxcensus`; the
census files are fetched once and cached.

```bash
uv run eodgdl reweight build --data data --out output/reweight   # build, write, check
uv run eodgdl reweight check output/reweight                     # check a set again
```

`check` reads the files back the way the tool's loaders do (integer keys, unique ids, joins,
every TAZ mapped, every map geography present in every constraint file, every positive
target with at least one matching record) and lists what would fail.
